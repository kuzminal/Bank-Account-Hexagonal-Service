# 0004. Transactional Outbox для надёжной публикации событий

- **Статус:** Accepted
- **Дата:** 2026-11-11

## Контекст

Изначально событие записывалось в БД и отправлялось в Kafka двумя отдельными шагами
(dual-write): сначала `repository.save(...)`, затем `notification.notify(...)`.

Возможные проблемы:
- если Kafka недоступен после коммита в БД — событие теряется;
- если коммит в БД откатывается после отправки — сообщение «призрачно» ушло потребителю.

Нарушается атомарность между состоянием агрегата и публикацией события.

## Решение

Внедрён паттерн **Transactional Outbox**:

1. доменное событие сериализуется в JSON и сохраняется в таблицу `outbox_event`
   **в той же транзакции**, что и изменение агрегата (через порт `OutboxRepositoryPort`);
2. компонент `OutboxRelay` (`@Scheduled`) периодически забирает неотправленные записи
   и публикует их в Kafka с ключом по `aggregateId`;
3. отметка `sent` ставится только после успешной отправки — гарантия **at-least-once**;
4. потребители должны быть идемпотентны (дедупликация по `eventId`).

## Последствия

**Плюсы:**
- атомарность записи состояния и публикации события;
- отсутствие потерь событий при сбоях Kafka;
- порядок событий одного счёта сохраняется (ключ партиции = `aggregateId`).

**Минусы:**
- дополнительная таблица и процесс relay — рост сложности;
- доставка at-least-once требует идемпотентности потребителей.
