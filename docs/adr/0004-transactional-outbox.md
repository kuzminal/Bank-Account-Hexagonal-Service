# 0004. Transactional Outbox для надёжной публикации событий

- **Статус:** Proposed
- **Дата:** 2026-11-10

## Контекст

Сейчас событие записывается в БД и отправляется в Kafka двумя отдельными шагами
(dual-write): сначала `repository.save(...)`, затем `notification.notify(...)`.

Возможные проблемы:
- если Kafka недоступен после коммита в БД — событие теряется;
- если коммит в БД откатывается после отправки — сообщение «призрачно» ушло потребителю.

Нарушается атомарность между состоянием агрегата и публикацией события.

## Решение

Внедрить паттерн **Transactional Outbox**:

1. доменное событие сохраняется в outbox-таблицу **в той же транзакции**, что и
   изменение агрегата;
2. отдельный процесс-relay (или Debezium CDC) читает outbox и публикует события в Kafka
   с гарантией **at-least-once**;
3. потребители идемпотентны — дедупликация по `eventId`.

## Последствия

**Плюсы:**
- атомарность записи состояния и публикации события;
- отсутствие потерь событий при сбоях Kafka.

**Минусы:**
- дополнительная таблица и процесс relay (или инфраструктура CDC) — рост сложности;
- доставка at-least-once требует идемпотентности потребителей.
